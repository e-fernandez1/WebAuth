The Authentication Flow

Click any step to expand the technical detail. Every step you see is what actually executes when you create an account or log in on this site.

  1. 1 Sign Up User submits username, email, password

    The server normalizes the email through email-validator, rejects duplicates, and runs the password through the same validate_password() function that backs the live indicator on the form.

    Failed: weak password, duplicate user, or malformed email → logged as signup_fail in the audit log.

  2. 2 Email Confirmation A 6-digit code is sent to the address; only confirmation creates the account

    The bcrypt hash and unverified data are stored in PendingSignup. No User row is created until the code matches. Codes expire after 10 minutes; any prior pending signups for the same email are dropped.

    Without this gate, an attacker could squat on someone else’s username paired with their own email.

  3. 3 Password Hashing bcrypt with per-user salt, cost factor 12

    The plaintext password is fed to bcrypt.hashpw(password, bcrypt.gensalt(rounds=12)). The output is a 60-byte string that includes the algorithm version, cost, salt, and hash. The plaintext is never written to disk and never compared as plaintext.

    Cost 12 means each verification takes ~250ms — barely noticeable for one user, prohibitively slow for an offline brute-force attacker.

  4. 4 Login: Password Check bcrypt verifies in constant time

    The IP is rate-limited first (5 attempts/min). If allowed, bcrypt.checkpw(submitted, stored_hash) rehashes the candidate with the stored salt and compares in constant time, defeating timing oracles. The same generic “Invalid credentials” message is returned whether the username doesn’t exist or the password was wrong — no enumeration leak.

    No session is granted yet. Even a correct password isn’t enough.

  5. 5 Two-Factor: Email Code 6-digit one-time code, single-use, 5-min expiry

    A code generated with secrets.randbelow(1_000_000) is emailed to the user. Any prior unused code for that user is invalidated, so a stolen code from a previous session is worthless. The verify endpoint is independently rate-limited.

    The 1-in-a-million guess rate combined with rate limiting caps an attacker at roughly 25 attempts per code window.

  6. 6 Session Issuance Signed cookie, HttpOnly + SameSite + Secure

    Only after the 2FA code matches is login_user() called and the Flask session promoted to logged-in. The cookie is signed (tampering invalidates the signature), HttpOnly (JavaScript can’t read it), SameSite=Lax (defeats most CSRF), and Secure in production (HTTPS only).

    Logout invalidates the session immediately; the 12-hour lifetime caps how long a stolen cookie remains useful.

  7. 7 Audit & Security Center Every event logged; users see their own history

    Every signup, login, 2FA verification, logout, rate-limit, and admin action writes a row to AuthEvent with the user, IP, browser/OS/device, and geolocation. The Personal Security Center on the dashboard surfaces this back to the user so they can spot a login they didn’t make.

    Authentication that you can’t see isn’t authentication you can trust.
