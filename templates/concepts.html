Authentication Concepts

Plain-English explainers of every idea this site is built on. Each section pairs the concept with how WebAuth actually applies it.

1. Password Hashing

A hash function turns any input into a fixed-length string of garbage. The trick that makes hashing useful for passwords is that it’s one-way: easy to compute the hash from the password, infeasible to reverse the hash back into the password.

When you sign up, the server computes hash(password) and stores only the hash. When you log in, it computes hash(submitted_password) and compares it to the stored hash. If they match, the password was right — without the server ever needing the plaintext.

Why it matters: if an attacker steals the database, they get hashes, not passwords. With a slow hash function, brute-forcing each user’s password individually takes years.

In WebAuth

Passwords are hashed with bcrypt at cost 12 before any database write. Plaintext is never stored. The verification function performs a constant-time comparison so an attacker can’t use timing differences to leak the answer.

2. Salt

A salt is a random value added to each password before hashing. Two users with the same password get different salts and therefore different hashes.

Without a salt, an attacker can precompute a giant lookup table mapping common passwords to their hashes (a “rainbow table”) and crack every user with the same password in one shot. Salt destroys this shortcut: the attacker has to brute-force every user separately.

In WebAuth

bcrypt generates a 16-byte random salt for every user. The salt is embedded in the stored hash itself, so it travels with the password and never has to be tracked separately.

3. bcrypt and the Cost Factor

bcrypt is a hash function specifically designed to be slow, on purpose. The cost factor controls how slow: each cost increment doubles the work. Cost 12 means roughly 250 ms per hash on commodity hardware.

250ms is fine when you log in once. It’s a disaster for an attacker trying a billion passwords offline — that’s 8,000 years of pure compute per user. The same hash function that took milliseconds for the legitimate user makes the attack mathematically uneconomic.

In WebAuth

Cost 12 was picked as the standard production setting in 2026. As hardware gets faster, cost factors are raised in lockstep so the wall-clock cost of an attack stays high.

4. Two-Factor Authentication

A factor is something the user has, knows, or is. Passwords are “something you know.” A second factor is something separate — a phone, a security key, an email inbox, a fingerprint. The point: even if your password is stolen, the attacker still needs your second factor.

Common second factors: SMS codes (weak, SIM swappable), authenticator app TOTPs (good), email codes (frictionless, depends on email security), hardware keys / WebAuthn (strongest).

In WebAuth

After a correct password, a 6-digit code is emailed to the registered address. The code is generated with secrets.randbelow (cryptographically secure, not predictable), single-use, and expires in 5 minutes. Issuing a new code invalidates the previous one, so a stolen code from a prior session is worthless.

5. Sessions and Cookies

HTTP is stateless — the server doesn’t remember you between requests. To stay logged in, your browser sends a session cookie with every request. The server checks the cookie to confirm who you are.

The cookie has to be unforgeable, so the server signs it with a secret key. If anyone tampers with the cookie, the signature breaks and the server rejects it.

Three cookie flags do most of the heavy lifting:

  • HttpOnly — JavaScript can’t read the cookie, so even an XSS bug can’t exfiltrate the session token.
  • SameSite=Lax — the browser refuses to send the cookie on cross-site POSTs, defeating most CSRF attacks.
  • Secure — the cookie is only sent over HTTPS, so it can’t leak over plain HTTP.

In WebAuth

Flask-Login signs the session cookie with the server’s SECRET_KEY. All three flags are set; Secure activates automatically in production. Sessions expire after 12 hours, capping how long a stolen cookie remains useful.

6. HTTPS / TLS

Every byte that leaves your browser passes through routers, ISPs, and possibly someone’s coffee-shop Wi-Fi access point. HTTPS wraps the connection in a TLS tunnel: the contents are encrypted end-to-end, so nobody between you and the server can read them.

HSTS (HTTP Strict Transport Security) is a header that tells the browser “always use HTTPS for this site, never plain HTTP.” Once received, the browser remembers it for the duration specified, defeating downgrade attacks.

In WebAuth

In production, the site is served by Render with a Let’s Encrypt certificate over TLS 1.3. The HSTS header is set with max-age=31536000 (one year) plus includeSubDomains.

7. Rate Limiting

If an attacker can submit a million login attempts per second, even slow bcrypt won’t save you. Rate limiting caps how many attempts any one source can make in a given window. The simplest version: count attempts per IP, return HTTP 429 (Too Many Requests) past a threshold.

Rate limiting buys time. Combined with hashing, it shrinks the attacker’s attack rate from millions of guesses per second to handfuls per minute.

In WebAuth

A sliding-window counter caps every IP at 5 attempts per minute on login, 5 on signup confirmation, and 5 on 2FA verification — three independent buckets, so exhausting one doesn’t affect the others. Triggering the limit returns HTTP 429 and writes a rate_limited audit row.

8. Audit Logging

If you can’t see authentication events, you can’t notice when something goes wrong. An audit log records every signup, login, 2FA attempt, logout, and admin action with enough context (user, IP, time, browser) to reconstruct what happened.

For users: the audit log surfaces “who logged in as you, from where, when” so they can spot a takeover. For operators: it shows attack patterns — brute force, credential stuffing, geographic anomalies.

In WebAuth

Every authentication event becomes an AuthEvent row with username, IP, browser/OS/device, country/city, event type, and a free-text detail field. The user dashboard shows your own history; the analytics dashboard shows aggregates; the admin console shows everything.
